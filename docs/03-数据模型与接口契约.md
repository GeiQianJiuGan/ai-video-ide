# 数据模型与接口契约

> 配套：[01-技术栈与架构](01-技术栈与架构.md) · [02-功能开发文档](02-功能开发文档.md)

## 0. 通用约定

- 主键：字符串 ULID（`chr_01H...` 前缀区分类型），时间可排序、跨机器不冲突。
- 时间：UTC ISO8601 存储，前端本地化显示。
- 所有表含 `created_at / updated_at`；软删除仅用于 Character/Location/Prop（`deleted_at`），生成版本不软删。
- 文件路径：**相对工程根目录**，正斜杠。
- 枚举在 Python `StrEnum` 与 TS 联合类型两侧生成，单一来源为后端 OpenAPI。

## 1. 实体关系总览

```text
Project
 ├─ Character ─┬─ Appearance(自引用 parent) ─┬─ CharacterSheet ─ SheetVersion
 │             └─ (default_appearance_id)     └─ view_regions
 ├─ Location ── LocationVariant ── LocationReference(版本)
 ├─ Prop ── PropReference(版本)
 ├─ Story(1:1) ── Scene ─┬─ SceneCast(→Character, Appearance)
 │                       └─ Shot ─┬─ ShotCast(→Character, Appearance, state)
 │                                ├─ ShotProp
 │                                ├─ ShotDependency(→Shot, strength)
 │                                ├─ PromptVersion
 │                                ├─ ShotContextOverride
 │                                └─ GenerationVersion ── (files)
 ├─ Workflow ─┬─ WorkflowCapability
 │            └─ WorkflowBinding
 ├─ Job ── JobDependency
 ├─ Asset (统一登记表，指向具体文件)
 ├─ ImportSession ── Clip ── ClipVersion        (阶段二)
 └─ Timeline ─ Track ─ TimelineClip ─┬─ Transition
                                     ├─ ClipEffect
                                     └─ Subtitle / AudioClip
```

### 2.9 应用级素材库（`library.db`，独立于工程）

### 2.10 幕流程图：衔接与 AI 导演（迁移 `0004_scene_flow`，schema → 4）

两级场景系统的第一级需要两样在别处放不下的东西——**衔接**与**协作记录**。
实现见 `persistence/models_flow.py`。

```sql
CREATE TABLE scene_link (            -- 「这一幕接下一幕」是一等公民，不是某个字段
  id TEXT PRIMARY KEY,               -- lnk_<ULID>
  from_scene_id TEXT NOT NULL REFERENCES scene(id) ON DELETE CASCADE,
  to_scene_id   TEXT NOT NULL REFERENCES scene(id) ON DELETE CASCADE,
  mode TEXT NOT NULL DEFAULT 'cut',  -- cut|transition|tail_frame
  shot_id TEXT,                      -- transition 生成出来的那个镜头；**不是外键**
  duration REAL NOT NULL DEFAULT 1.5,-- 转场秒数，只有 transition 用
  prompt TEXT,                       -- 转场画面描述；留空时由两幕标题拼一句
  created_at TEXT, updated_at TEXT,
  UNIQUE(from_scene_id, to_scene_id) -- 同一对场景之间只允许一条
);
CREATE INDEX idx_scene_link_from ON scene_link(from_scene_id);
CREATE INDEX idx_scene_link_to   ON scene_link(to_scene_id);

CREATE TABLE director_turn (         -- AI 协作栏的对话与提案，只增不改
  id TEXT PRIMARY KEY,               -- dtn_<ULID>
  role TEXT NOT NULL DEFAULT 'user', -- user|assistant|proposal|applied
  content_json TEXT NOT NULL DEFAULT '{}',
  created_at TEXT
);

-- 0005_scene_nodes：节点里的「小节点」。两张表都是**全量替换**（整表重写），
-- `index_no` 就是显示与优先级顺序，所以传进来的顺序有意义。
CREATE TABLE scene_cast (            -- 人物小节点：这一幕有哪些形象
  id TEXT PRIMARY KEY,               -- scc_<ULID>
  scene_id TEXT NOT NULL REFERENCES scene(id) ON DELETE CASCADE,
  appearance_id TEXT NOT NULL REFERENCES appearance(id) ON DELETE CASCADE,
  index_no INTEGER NOT NULL DEFAULT 0,
  created_at TEXT
);
CREATE INDEX idx_scene_cast_scene ON scene_cast(scene_id);

CREATE TABLE scene_location (        -- 地点小节点：**index_no = 0 那条是主地点**
  id TEXT PRIMARY KEY,               -- scl_<ULID>
  scene_id TEXT NOT NULL REFERENCES scene(id) ON DELETE CASCADE,
  location_variant_id TEXT NOT NULL REFERENCES location_variant(id) ON DELETE CASCADE,
  index_no INTEGER NOT NULL DEFAULT 0,
  created_at TEXT
);
CREATE INDEX idx_scene_location_scene ON scene_location(scene_id);
```

`scene` 表另加一列：`prompt TEXT`（小节点里唯一必填的那个，镜头级 prompt 优先、空着才用它）。
`location_variant_id` 保留为「主地点」，始终等于 `scene_location` 里 `index_no = 0` 的那条。

> **0006_shot_adopted_video**：`scene` 上曾经还有一列 `main_version_id`（「采用为这一幕主视频的
> 那条版本」）。它是个错的层级——一幕下面有很多镜头，每个镜头各自独立生成很多段视频，
> 「用哪一段」只能一个镜头一个镜头地定；而且镜头一搬到别的幕，那个指针就发霉，只能靠 `issues`
> 报「已失效」。这条迁移把它回填进 `shot.current_version_id` 后删掉该列，从此全工程只有**镜头级
> 一个**「用哪一段」的指针（时间线装配、下游镜头抽末帧认的都是它）。

`shot` 表多一列 `kind TEXT NOT NULL DEFAULT 'shot'`（`shot|transition`）。

三种 mode 全部落到**已有机制**上，不新造概念：

| mode | 落到什么 |
| --- | --- |
| `cut` | 什么都不生成。 |
| `transition` | 生成一段 1~2s 转场 → `Shot.kind='transition'`，**挂在 from_scene 下、`index_no` 排最后**。`timeline.auto_assemble` 按 `scene.index_no + shot.index_no` 排序，天然把它放在两幕之间，导出逻辑一行不用改。 |
| `tail_frame` | 只把下游首镜头的 `prev_shot_id` 指到上游末镜头，复用已有的 `depends_on` / `wait_reason`——「等上游末帧」照旧是可解释的等待。 |

`director_turn` 存的是**提案**而不是改动：`role='proposal'` 那条的 `content_json.ops` 是一个
`{op, target, temp_id, before, after, why, warnings}` 数组，数据库里一行都还没变。
用户逐条采用后才写库，并追加一条 `role='applied'` 记录（`{applied, failed, count}`）。
提案落库是为了**活过刷新**——审阅到一半刷新页面就白干了。

### 2.11 镜头之间的衔接（迁移 `0012_shot_link`，schema → 12）

两幕之间要衔接，**两个镜头之间同样要**：能引用设定图的模型往往做不了严格首尾帧，
反过来能严格首尾帧的又引用不了设定图，所以「两镜之间补一段短转场」是这类模型下
唯一能把画面接上的路。表结构与 `scene_link` 是同一套，只是两头指向 `shot`：

```sql
CREATE TABLE shot_link (             -- 「这一镜接下一镜」；没有行 = 无转场
  id TEXT PRIMARY KEY,               -- slk_<ULID>
  from_shot_id TEXT NOT NULL REFERENCES shot(id) ON DELETE CASCADE,
  to_shot_id   TEXT NOT NULL REFERENCES shot(id) ON DELETE CASCADE,
  mode TEXT NOT NULL DEFAULT 'cut',  -- cut|transition —— **刻意没有 tail_frame**
  shot_id TEXT,                      -- transition 补出来的那个镜头；**不是外键**
  duration REAL NOT NULL DEFAULT 1.5,-- 0.5 ~ 4.0 秒，只有 transition 用
  prompt TEXT,                       -- 转场画面描述；留空时由两镜标题拼一句
  created_at TEXT, updated_at TEXT,
  UNIQUE(from_shot_id, to_shot_id)   -- 同一对镜头之间只允许一条 → 所以是 PUT
);
CREATE INDEX idx_shot_link_from ON shot_link(from_shot_id);
CREATE INDEX idx_shot_link_to   ON shot_link(to_shot_id);
```

四条与 `scene_link` 不同的地方，都是为了不制造第二处配置：

- **没有 `tail_frame`**：镜头级的「续接末帧」早就有表达方式了（`Shot.prev_shot_id`），
  再给它一个同义词只会让两处配置打架；
- **没有行就是 `cut`**：老工程一行不用建，界面上画那条线也不需要先落库；
- **两头必须同幕且相邻**（按 `index_no`），否则 `VALIDATION_ERROR` 并在建议里说清
  「跨幕请用幕与幕之间那条衔接」；
- 补出来的转场镜头**排在这两镜之间**（`index_no` 插在中间，后面整体后移），
  于是 `timeline.auto_assemble` 的排序照旧把它放在正确位置，导出逻辑一行不用改。

**「转场暂未生成」只有一个判断依据**：`GET /storyboard` 每条连接器上的
`pending = (mode == 'transition' and not generated)`，其中 `generated` 说的是那个转场镜头
**已经有成片**（`current_version_id` 非空）。镜头造出来了但任务还在排队时它仍然是
`pending`——界面不要拿 `transition_shot_id` 再算一遍，否则一入队就会谎报「已生成」。

**「现在能不能补」是另一件事**，走连接器上另外三个字段（`pending` 的语义一个字都不改）：

| 字段 | 含义 |
| --- | --- |
| `blocked` | 这一条现在补不了的原因，如「Shot 1、Shot 2 还没有生成视频——转场要把前后两段真实成片接上」；能补时是 `null` |
| `blocked_how` | 配套的下一步（`story.FOOTAGE_HOW`：「先把这两个镜头各自生成出来，再补它们之间的转场」）；能补时是 `null` |
| `can_generate` | `pending and not blocked`——分镜板上那个「生成」按钮**只认它**，被拦下时按钮 `disabled` 且把 `blocked` 写进 tooltip |

**转场要接缝两侧都已经生成过视频才补得出来**：上游没出片就没有真末帧、下游没出片就没有
真首帧，此时补一段两头都对不上的过渡只会让接缝更明显。门槛只有一处口径
（`services/story.py::has_footage` / `footage_blocker` / `FOOTAGE_HOW`），四个入口全都过它：
`sequence.transition_plan`（被拦的进 `plan.blocked` 并写进 `notes`）、`sequence.plan`
（那条边 `will_create_transition=false` + `blocked`）、以及 `_make_transition` /
`_make_shot_transition` 两条写路径（绕开账单直接指名一条时报 `MISSING_INPUT`
「转场要等前后都出片」）。带 `only` 跑一条被拦的衔接**不是失败**：它进 `skipped` 并带上原因。

由此还有一个可见后果：全新工程第一次跑 `POST /sequence/run` 一段转场都不会补
（那时一个镜头都还没出片），账单的 `notes` 会把这句话说出来——等这一轮镜头出片后，
在分镜页按一次「一键生成转场」就补上。

### 2.12 镜头上的首帧 / 末帧槽位（迁移 `0013_shot_frames`，schema → 13）

**「哪一张是首帧」得是用户按下去的那一下。** 以前镜头上没有这个字段，于是上下文账单只好把
优先级最高的那一条（通常是角色三视图）自动提拔成首帧：界面上给一张三视图标了「首帧」，
模型端也真把它当画面第一格用。首尾帧决定「画面从哪一格开始 / 结束」，参考素材决定
「谁出场、在哪儿、动作什么样、跟着哪段声音」——两件事，两处表达，所以镜头上补两列：

```sql
ALTER TABLE shot ADD COLUMN first_frame_asset_id TEXT;  -- 空 = 没有指定
ALTER TABLE shot ADD COLUMN last_frame_asset_id  TEXT;  -- 空 = 只做 i2v，不做 flf
```

四条规矩：

- **只能是图片**：模型端那两个入口接的是 LoadImage 那类节点，挑了视频 / 音频报 `422`
  `VALIDATION_ERROR`「首帧只能是图片」；
- **清空要传 `''`**，不是 `null`——`ShotPatch` 走 `exclude_none`，`null` 会被当成「这次不改」；
- **刻意不加外键**（与 `shot.current_version_id` 同理）：资产被删掉时按「这个镜头没有首帧」
  处理，而不是让删除操作被外键挡下来。所以 `GET /shots/{id}` 除了两个 id 还回
  `first_frame_path` / `last_frame_path`，资产行已经没了时是 `null`，界面照此显示
  「指定的图已不在」而不是画一个碎图标；
- **空 ≠ 没有首帧**：`tail_frame` 衔接的镜头照旧用上游那张抽出来的真末帧
  （`prev_shot_id` + `services/frames.py`）。顺序只有两级，见下面 3.2 的 `role`。

老工程升上来只是多了两个空列，行为不变——真正的行为变化在
`services/context.py::_assign_roles`（不再提拔参考素材），不需要迁移。


### 2.13 片段的来路（迁移 `0014_clip_origin`，schema → 14）

时间线上的片段以后有三种来路，装配对帐时必须分得清「这条是我上次自动装的」和
「这条是用户手摆的」——不然重新装配会把手摆的那些默默冲掉：

```sql
ALTER TABLE timeline_clip ADD COLUMN origin TEXT NOT NULL DEFAULT 'manual';
-- assembled = 自动装配铺的（重新装配时按镜头对帐，可以被移动 / 删除）
-- manual    = 用户手摆的、长视频切出来的段、自己加的素材（装配**永不触碰**）
UPDATE timeline_clip SET origin = 'assembled'
 WHERE shot_id IS NOT NULL AND version_id IS NOT NULL;  -- 老数据回填
```

回填刻意**先全置 `manual` 再挑出装配铺的那些**：认不出来的片段一律落在「装配不碰」这一侧，
宁可少管，不可误删。两个层级就是靠这一列共处一条时间线的——装配按「幕序 + 镜头序」对帐自己
铺的那些（导入的幕与剧本的幕一视同仁，所以两者能随意穿插），用户手摆 / 手拖进去的一律
`manual`，重新装配一段都不动（返回值里的 `preserved` 就是它们）。

### 2.14 幕的来源与参数模式（迁移 `0015_scene_kind_params`，schema → 15）

长视频导入的幕与剧本拆出来的幕**必须是同一种东西**（否则顺序、装配、导出、二次处理都得写
第二份），差别只落在两列上：

```sql
ALTER TABLE scene ADD COLUMN kind       TEXT NOT NULL DEFAULT 'storyboard'; -- storyboard | ingested
ALTER TABLE scene ADD COLUMN param_mode TEXT NOT NULL DEFAULT 'per_shot';   -- per_shot | shared
ALTER TABLE scene ADD COLUMN params_json TEXT;         -- 幕级共用参数（镜头留空时继承它）
ALTER TABLE scene ADD COLUMN source_asset_id TEXT(40); -- kind='ingested' 时那段源成片
```

两条不许绕的规矩：

- **`kind` 不参与生成路径的分支**（硬约束 1 的延伸）：完整性要求查表
  `services/params.py::SCENE_REQUIRED`（`storyboard` 要 prompt / 地点 / 出场表，
  `ingested` **什么都不必填**——不然会得到「请给这一幕写 prompt」这种荒谬的门槛）；
- **`param_mode` 只决定「新建镜头要不要预填」**，参数解析永远只看「镜头上那一项空不空」：
  `per_shot` 是建镜头那一刻把幕级值抄过去（剧本拆分镜的老行为），`shared` 一个字段都不抄，
  留空 = 解析时回退到幕（改一处三十段跟着变，长视频默认）。三级继承在
  `services/params.py`：**工程 → 幕 → 镜头**，只有一份口径。

### 2.15 版本的血缘与区间（迁移 `0016_version_lineage_range`，schema → 16）

```sql
ALTER TABLE generation_version ADD COLUMN parent_version_id TEXT(40); -- 从哪一版处理来的
ALTER TABLE generation_version ADD COLUMN in_point  REAL;             -- 只用源文件的这一段
ALTER TABLE generation_version ADD COLUMN out_point REAL;
```

- `parent_version_id` 是**二次处理的血缘**（原始 v1 → 超分 v2 → 插帧 v3）：版本轨靠它画一条线
  而不是几条互不相干的版本，`GET /versions/{vid}/lineage` 就是它。仍然只增不改（硬约束 3）；
- `in_point` / `out_point` 是**「这一版只用源文件的这一段」**——长视频切段靠它做到**零文件复制**：
  一幕下面 N 个镜头各一版，`asset_id` 全部指向同一个源文件，各自带区间。装配时抄进
  `timeline_clip`，导出时 ffmpeg 用 `-ss/-to` 各取一段。真去切 60 个文件的话，磁盘翻倍，
  切点还会被关键帧对齐悄悄挪动。

### 2.16 第二个采用指针：声音（迁移 `0017_shot_audio_version`，schema → 17）

```sql
ALTER TABLE shot ADD COLUMN current_audio_version_id TEXT(40);
```

「换一条声音」不该是「把画面重跑一遍」。声音是**同一个镜头上 `kind="audio"` 的另一版**，
采用指针与画面那个互不干扰：`current_version_id` 决定用哪一段画面，
`current_audio_version_id` 决定用哪一条声音，两个都走全工程唯一那个采用入口
`POST /versions/{vid}/current`（它按 `version.kind` 决定落哪个指针）。
装配时音频版本落到专门的配音轨并把画面那一段 `muted=1`，时间线一行不用改。
**不加外键**（与另一个指针同理）：版本被删时按「这个镜头没有配音」处理。

### 2.17 台词（迁移 `0018_shot_dialogue`，schema → 18）

```sql
ALTER TABLE shot  ADD COLUMN dialogue TEXT;  -- 这个镜头说的话
ALTER TABLE scene ADD COLUMN dialogue TEXT;  -- 整幕的兜底（旁白那类）
```

为什么不塞进已有的列：`description` 是**画面**描述，`prompt` 是喂给视频模型的正向提示词——
把台词塞进任何一个，都会让它跟着进画面那条链，模型会试着把字画出来。

**视频那条链一个字都不读它**，所以它不在任何完整性要求里：没有台词的镜头照样能出画面，
空 = 这个镜头不说话。台词从哪来只有一份口径（`services/dub.py::text_of`）：
**显式传入 → 镜头的 `dialogue` → 幕的 `dialogue`**。幕级兜底是刻意的——长视频切出来的镜头
本来就没有台词，整幕配同一段旁白很常见。

### 2.18 工程路由（迁移 `0022_project_route`，schema → 22）

```sql
-- SQLite 没有 ALTER COLUMN，这条走 batch_alter_table 重建表
ALTER TABLE project ALTER COLUMN generation_mode DROP NOT NULL;  -- 可空，默认 ''
UPDATE project SET generation_mode='comfy_workflow' WHERE generation_mode='workflow_api';
UPDATE project SET generation_mode='' WHERE generation_mode IS NULL OR generation_mode='comfy_preset';
```

`project.generation_mode` 这一列从 `0009` 就在库里，但**到这条迁移之前从来没有被读过**：
入队时是 `generation_mode = "comfy_preset"` 写死的、执行时是 `registry.provider("comfy_preset")`
写死的——界面上选了「通用 REST API」或「ComfyUI 工作流绑定」，后端照旧提交给 ComfyUI 预设，
**选了等于没选**，而冻结进版本的参数里还写着用户选的那条路（破硬约束 3、4）。

改成真的会被读之后，这一列要能表达第三种状态：

| 值 | 含义 |
| --- | --- |
| `''`（空串） | **跟随设置页**（应用级 `video.provider`）。绝大多数工程是这一种 |
| `comfy_preset` / `http_api` / `comfy_workflow` | 这个工程**显式**走这条路，从此不跟设置页变 |

三件事各有理由：**列改可空**是为了让「继承」有地方表达；**`workflow_api` → `comfy_workflow`**
是因为同一条路曾经有两个名字（工程列与 `api/workflows.py` 用前者，registry 与设置页用后者，
中间没有任何映射），归一到 registry 那个名字，读写两侧再各过一次 `route.normalize()` 收老客户端；
**把等于旧默认值的行清成空串**不丢用户意图——这一列从来没被读过，`comfy_preset` 是建工程时
无条件写进去的，不是谁选的，清成「继承」之后行为与升级前逐字相同，但改了设置页之后老工程
会跟着变，这才是用户预期。

`job` / `generation_version` **一列都不动**：路由是**入队时解析一次并冻结进
`job.params_json["route"]`** 的（照硬约束 3 的作风），执行与重试只读冻结值。给它们加列只会
多出一份会和 `params` 打架的真源。冻结的形状见 3.4。

#### 3.2.1 实现口径：`role` / `media` / `capacity`（`services/context.py`）

落地时账单每条多了三样东西，`GET /shots/{id}/context` 与冻结进
`GenerationVersion.context_json` 的都是这个形状：

```json
{
  "items": [
    { "key": "first_frame", "kind": "first_frame", "label": "雨夜巷口 · 首帧",
      "asset_id": "ast_9", "path": "assets/images/xxx.png", "media": "image",
      "priority": 130, "included": true, "role": "first_frame", "over_capacity": false },
    { "key": "char:chr_1", "kind": "character_sheet", "label": "林小雨（常服）",
      "media": "image", "priority": 100, "included": true, "role": "reference",
      "desc": "褪色军绿夹克，左肩有补丁", "desc_missing": false },
    { "key": "manual:ast_31", "kind": "manual", "label": "推轨参考",
      "media": "video", "priority": 110, "included": true, "role": "reference",
      "desc": "", "desc_missing": true }
  ],
  "capacity": {
    "limit": 9, "source": "wan-r2v", "detail": "项目预设 wan-r2v 标了 9 个 AIVS_REF_* 槽位。",
    "ref_count": 5, "dropped": 0, "dropped_labels": [], "over": false,
    "media": {
      "image": { "label": "参考图",   "limit": 9, "ref_count": 4, "dropped": 0,
                 "dropped_labels": [], "over": false },
      "video": { "label": "参考视频", "limit": 0, "ref_count": 1, "dropped": 1,
                 "dropped_labels": ["推轨参考"], "over": true },
      "audio": { "label": "参考音频", "limit": 0, "ref_count": 0, "dropped": 0,
                 "dropped_labels": [], "over": false }
    }
  }
}
```

| 字段 | 口径 |
| --- | --- |
| `role` | `first_frame` / `last_frame` / `reference`，未采用的是空串。**唯一真源是 `context._assign_roles`**，`services/generation.py::_images_of` 照它读，不再自己挑一遍 |
| `media` | `image` / `video` / `audio`，只看后缀（`assets.kind_of_suffix`）。认不出后缀的条目**进账单但不采用**，理由写在条目上 |
| `desc` | 这一条进 prompt 时那句「长什么样」——**模型引用这个素材时唯一看得到的说明**。取值口径只有 `context._desc_of()` 一处：素材自己那句 `Asset.description` → 退回实体设定文字（形象外形 / 变体描述 / 道具描述）→ 空。**账单留全文**，截断只发生在 `providers/base.py::clip_desc`（`DESC_MAX = 120`） |
| `desc_missing` | `desc` 是空串。**由后端算一次**，两个前端渲染处（`ShotView` / `SceneWorkbench`）照它标「没有描述 · 模型只看到一个文件名」，不各算一遍 |
| `capacity.limit` | `null` = 不限（通用 REST 合同 / 还没选预设）。**0 是有意义的答案**：那份图一个 `AIVS_REF_*` 都没标 |
| `capacity.source` / `detail` | 这个数字哪来的（预设名 / 「REST 合同」）。**上限由适配层回答**，不是应用级设置——`video.ref_limit` 已经不再是上限来源 |
| `capacity.media.*` | 三族分开算：图片数 `AIVS_REF_*`、视频数 `AIVS_REF_VIDEO_*`、音频数 `AIVS_REF_AUDIO_*`。混着数会把「图多音频少」报成装得下 |
| 顶层 `ref_count` / `dropped` / `dropped_labels` | **说的是参考图**（历史口径，旧版本冻结的账单照它读）；`over` 是「任意一族装不下」 |
| `over_capacity` | 这一条采用了、但这份图收不下（一定是每族末尾几条，适配器按顺序填槽位）。「采用了但喂不进去」和「没采用」是两件事，界面必须分得开 |

**首尾帧的判定顺序只有两级**：镜头上那两个显式槽位（`Shot.first_frame_asset_id` /
`last_frame_asset_id`）→ 首帧没指定而这个镜头要续接上游时用 `prev_frame` 那张真末帧 →
**到此为止**。绝不把优先级最高的参考素材提拔成首帧。

**账单不截断**：采用的照样全采用，超出槽位的部分变成生成前的一次确认（见下面生成入口的
`REF_OVER_CAPACITY` / `allow_ref_drop`），真正的截断只发生在提交那一刻并如实写进
`params.ref_notes` / `params.refs`（每项 `{label, kind, media, file, desc}`——`desc` 是**全文**，
进 prompt 前那道 120 字截断只发生在 `providers/base.py::clip_desc()` 里）。

### 3.4 Route（「这个工程 + 这个能力 → 走哪条路」唯一口径）

`backend/app/services/route.py`。**业务层里唯一一处按调用方式的名字分岔的地方就是这张表**
（硬约束 1），其余各处一律读 `binds`：

```python
BINDS = {"comfy_preset": "preset", "http_api": "base_url", "comfy_workflow": "workflow"}
INHERIT = ""                                 # 工程那一列留空 = 跟随设置页
ALIAS   = {"workflow_api": "comfy_workflow"} # 同一条路的老名字
```

`GET /projects/{pid}/route`（只读，**绝不抛**——用户正是来这儿看哪里不对的，缺什么在
`issues` 里而不是一个 5xx）：

```json
{
  "mode": "",
  "provider": "comfy_preset",
  "label": "ComfyUI 预设（默认）",
  "source": "default",
  "binds": "preset",
  "binds_workflow": false,
  "settings_provider": "comfy_preset",
  "options": [
    { "name": "", "label": "跟随设置页", "inherit": true, "binds": "" },
    { "name": "comfy_preset", "label": "ComfyUI 预设（默认）", "inherit": false, "binds": "preset" },
    { "name": "http_api", "label": "通用 REST API", "inherit": false, "binds": "base_url" },
    { "name": "comfy_workflow", "label": "ComfyUI 工作流绑定", "inherit": false, "binds": "workflow" }
  ],
  "capabilities": [
    { "capability": "image2video", "capability_label": "普通镜头（图生视频）",
      "provider": "comfy_preset", "label": "ComfyUI 预设（默认）", "source": "default",
      "binds": "preset", "binds_workflow": false,
      "preset": "U17-MiniMax-H3", "workflow_id": null, "workflow_name": null, "base_url": null,
      "ready": true, "issues": [],
      "slots": { "source": "U17-MiniMax-H3", "detail": "这份图标了 2 个参考图槽位…",
                 "image": 2, "video": 0, "audio": 0 } }
  ],
  "contract": ["服务端需要实现：POST {base}/submit → {task_id}", "…"]
}
```

`capabilities[]` 实际有两条（`image2video` 普通镜头 / `first_last_frame` 首尾帧衔接），
上面只列了第一条。**这两条可以给出不同答案**——预设那条路上它们绑的本来就是两份不同的图。

五条口径，各处只读这一份：

- **`mode` 是工程那一列的原样值，空串 = 跟随设置页**，不是「没配置」。所以 `provider`
  （最终走哪条）与 `source`（`project` / `settings` / `default`，这个答案是谁给的）要一起读——
  否则用户改了设置页也不知道哪些工程会跟着变。`settings_provider` 是「清空会回到哪条」。
- **`binds` 决定界面画哪一组控件**，不是调用方式的名字：`preset` 两份预设下拉 /
  `base_url` 一行地址说明 / `workflow` 四个能力下拉。`options[]` 每项也带 `binds`，于是
  「要改成哪一条才会绑图」由后端回答，前端一个调用方式的名字都不写死。
- **readiness 按能力算**：同一个工程的 `image2video` 与 `first_last_frame` 可以给出两个不同
  答案（预设那条路上两份图本来就不同）。`issues[]` 是四要素错误的数组，`suggestions`
  必须原样显示（硬约束 4）。
- **`slots` 按真正会提交的那一份数**：`null` = 不限（REST 整组发过去），**`0` 是有意义的答案**
  （绑的那份图一个参考图槽位都没标 / 绑定那条路只喂图片），两者不能都画成「—」。
  `source` / `detail` 说清这个数字是哪份图、哪条合同给的。
- **`base_url` 进得了这份契约，密钥永不进**（与「API key 永不回明文」同一条理由）。

**入队门槛在入队之前**：`route.require(pid, capability)` 不 ready 就抛 `issues[0]`
（缺地址 / 缺预设 / 没绑图统统在这一下挡住，队列里一条都不许留），随后
`route.frozen()` 整个写进 `job.params_json["route"]`：

```json
{ "provider": "http_api", "label": "通用 REST API", "source": "settings",
  "capability": "image2video", "workflow_id": null, "workflow_name": null,
  "preset": null, "base_url": "http://127.0.0.1:9/v1" }
```

**只有事实，没有当时的 readiness**：`ready` / `issues` 说的是解析那一刻缺什么，冻进去只会让
半年后翻参数的人把它当成这次任务的失败原因。执行读的是 `_provider_of(params)` 三级回退
（`params.route.provider` → `params.generation_mode` → `settings.video_provider`，最后一级是给
这次改造之前入队的老任务留的），所以**重试不重新解析**——否则「重试」会变成「换个后端跑一遍」，
而版本参数上写的还是旧那条。前端读冻结值只有一个口径：`shared/api/projects.ts::frozenRoute()`，
老任务没有这一项时回 `null` 而不是替它编一条。

## 4. REST 接口清单（`/api/v1`）

### 项目
```text

POST   /projects/open                   打开目录（校验/迁移 schema）

PATCH  /projects/{pid}                  更新设置

GET|PUT /projects/{pid}/workflow-bindings  调用方式 + 四个能力各绑哪份图；PUT 收整份（按值覆盖）
```

`PUT /preset` 与 `PUT /workflow-bindings` 的写入语义**刻意不同**，前端必须按各自的规矩发：
前者认「键在不在」（`"r2v_name" in payload`），所以**只发正在改的那个角色**——把界面上显示的
另一份（很可能是从设置页继承来的）原样回发，就把它从「跟随设置页」写成了「工程指定」，
此后设置页再改也带不动它。后者收整份 `model_dump()`，所以要**先合并再整份 PUT**。
另外 `PUT /preset` **不许顺手改路**（曾经它会把 `generation_mode` 写成 `comfy_preset`：
换一份预设把用户选的「通用 REST API」悄悄换掉了）。

```text

POST      /projects/{pid}/story/breakdown/apply   审阅后按选择落库          ※兼容路径
```

`story/breakdown` 那两条是**兼容路径**：接口与测试原样保留，但界面上已经没有入口了。
「把一段剧本拆成幕与镜头」现在走 AI 导演的分段工具循环（`read_script` + `add_scene` /
`add_shot`，见下面的「AI 导演」一节）——一次调用吐完整部剧本必然超时或被截断。

分镜板一条泳道里**卡片与线是两种主体**：`links[]` 是本幕内相邻两个正片镜头之间那条线
（按顺序，比卡片数少一条），`next_link` 是本幕到下一幕那条（最后一幕是 `null`）。
两级共用一种形状：`{id, level, mode, duration, prompt, transition_shot_id, generated, pending,
blocked, blocked_how, can_generate, …}`，
`id === null` 就是**后端连行都没有 = 无转场**。补出来的转场镜头**照旧在 `shots[]` 里**
（导出顺序、补首帧、时间线装配都靠它在那儿），前端把它从卡片行里挑出来画在线上而已。
按钮能不能点看 `can_generate`，不能点的原因在 `blocked`（详见上面 `shot_link` 那一段）。

`PATCH /shots/{shid}` 除了老字段还收那两个首 / 末帧槽位（表结构见 2.12）：

```text
PATCH /shots/{shid}   {first_frame_asset_id?, last_frame_asset_id?, …}
  —— 必须是**图片**资产，视频 / 音频报 422「首帧只能是图片」
  —— **清空传空串 `""`**：body 走 exclude_none，`null` 会被当成「这次不改」
GET   /shots/{shid}   除两个 id 外还回 first_frame_path / last_frame_path
  —— 资产行已经不在了（被删了）时是 `null`，界面显示「指定的图已不在」而不是画碎图标
```

**参考素材装不下是一次确认，不是失败**。账单采用的参考素材比模型端那份图能收的多时，
入队端点先回 `REF_OVER_CAPACITY`：**此时一个任务都没入队**（批量路径先扫完再动手），
`detail` 里按族写清「采用了几个、只能喂几个、会丢哪几个」。用户看清之后带
`allow_ref_drop=true` 重来一次同一个入口，才按槽位顺序喂前几个，丢了哪几个记进
版本参数 `ref_notes`（`refs` 记实际喂了哪几个）。带 `allow_ref_drop` 的入口有四个：
`/shots/{shid}/generate`、`/scenes/{sid}/generate`、`/sequence/run`、
`/sequence/transitions/run`——口径只有一份（`api/generation.py::_allow_ref_drop`）。

这条与 `check_context=false` 是两件不同的事：后者跳过的是**上下文完整性门槛**
（缺角色表 / 缺 prompt 那类），前者确认的是**槽位不够要丢素材**。

### 幕流程图 / 衔接 / 编排（两级场景系统的第一级）
```text
GET    /projects/{pid}/flow                       整张图：{nodes, links, note}
GET    /projects/{pid}/links                      衔接清单
PUT    /projects/{pid}/links                      upsert：{from_scene_id, to_scene_id, mode, duration?, prompt?}
DELETE /projects/{pid}/links/{link_id}            回到默认的 cut
POST   /projects/{pid}/sequence/plan              {mode} → 账单，**只算不做**
POST   /projects/{pid}/sequence/run               {mode, priority?} → 真入队
GET    /scenes/{sid}/videos                       这一幕**按镜头分组**的视频候选：{shots[], total, adopted_count, note}
```

镜头之间那条线是同一套东西（表结构见 2.11），所以接口形状也照抄一遍——**没有行就是无转场**，
所以 DELETE 与「切回 cut」是一回事：

```text
GET    /projects/{pid}/shot-links                  镜头衔接清单
PUT    /projects/{pid}/shot-links                  upsert：{from_shot_id, to_shot_id, mode, duration?, prompt?}
DELETE /projects/{pid}/shot-links/{link_id}        回到默认的 cut（已生成的那段转场镜头不跟着删）
POST   /projects/{pid}/sequence/transitions/plan   一键生成转场的账单：两级一起列，**只读、不抽帧、不入队**
POST   /projects/{pid}/sequence/transitions/run    {only?, priority?, allow_ref_drop?} → 按账单补，已出片的一条都不重做
```

`transitions/plan` 回 `{items, total, reused, blocked, notes}`：每条 `item` 带 `level`
（`shot` / `scene`，两级共用一种形状）、`link_id`、`where`（人话位置）、`duration` / `prompt`、
`shot_id` / `generated`、`will_generate`，以及这段转场两头的图从哪来——`first_frame` /
`last_frame` ∈ `real_frame`（真帧）/ `extract`（生成前会抽）/ `reference_image`（只能退回设定图）/
`waiting`（上游还没出片）/ `none`（取不到）。`transitions/run` 的 `only` 收的是**衔接 id**
（镜头级 / 幕级都认），分镜板上单条转场那个「生成」按钮走的就是它；跳过的每条都带
`reason` 或四要素错误，**绝不静默少做一件事**。

采用某一段**没有独立接口**：它就是「把这一版设成该镜头的当前版本」，走生成层里那唯一一个入口
`POST /projects/{pid}/versions/{version_id}/current`（硬约束 3）。`shots[]` 里每组带
`adopted_version_id` / `items` / `omitted`（不能当候选的附 `reason`），节点上则带 `video_shot_id`
与 `video_adopted`（播的这段不是采用的那一版时要标出来，不假装是）。

节点里的小节点（prompt 必填 / 人物 / 地点，各自上限 `scene.node_limit`，默认 9 且运行期可配）
走的还是 Scene 那组接口：

```text
GET      /scenes/{sid}                            单幕详情，含 prompt / cast / locations / node_limit
PATCH    /scenes/{sid}                            改 prompt 等字段（后端 exclude_none：清空要传 ""）
GET|PUT  /scenes/{sid}/cast                       {appearance_ids} 全量替换，可以是空数组
GET|PUT  /scenes/{sid}/locations                  {location_variant_ids} 全量替换；**第一条是主地点**
GET      /projects/{pid}/scene-node-options       挑小节点时的两张清单（带缩略图）
```

`scene-node-options` 回 `{cast[], locations[], node_limit, limit_hint}`：

```json
{ "cast": [ { "appearance_id": "app_x", "character_id": "chr_x", "character_name": "阿岚",
              "appearance_name": "默认形象", "label": "阿岚 · 默认形象",
              "is_default": true, "has_sheet": true, "thumbnail_path": "assets/sheets/a.png" } ],
  "locations": [ { "id": "lcv_x", "location_id": "loc_x", "variant_name": "雨夜",
                   "label": "王庭福地 · 雨夜", "thumbnail_path": null } ],
  "node_limit": 9, "limit_hint": "上限可改：设置页…" }
```

它存在的理由是**别让前端拼**：原来要按角色一个个拉 `appearances`（N+1），要图再按变体拉
`references`（又一轮 N+1），而 `角色 · 形象` / `地点 · 变体` 这个名字怎么拼只该有一处口径。
`thumbnail_path` 是**相对工程目录**的路径，前端过 `fileUrl(pid, path)` 取；没有图的条目给
`null` 但**仍留在清单里**——没有角色表的形象照样能挂，只是生成时喂不出参考图，界面标一下就行。
`GET /scenes/{sid}` 回的 `cast[]` / `locations[]` 里也各带一个 `thumbnail_path`（同一套口径），
所以挑人物 / 地点、看一幕挂了谁，界面上都是图而不是一串 id。
node 自己那个 `thumbnail_path` 是**这一幕的封面**，与这里的形象 / 地点缩略图不是一回事。

`flow` 的每个 node 是一幕：`{id, index_no, title, shot_count, generated_count,
transition_count, cast_names, duration_total, thumbnail_path, issues}`。
衔接是 **PUT upsert** 而不是 POST/PATCH 两条——「这两幕之间怎么接」只有一个答案，
同一对场景之间只允许一条边。

`plan` 与 `run` 是刻意分开的两步（照 `adopt/plan` 的习惯）：账单先说清
`{mode, total_jobs, transitions_to_create, ignored_transitions, scenes[], blockers[], notes[]}`，
看完了才动手。`run` 回来的 `skipped[]` 每条都带**四要素错误**——被跳过不是失败，
照常显示，不弹红叉。`sequential` 模式还会回一个 `chain[]`：每段拿上一段的真末帧当首帧，
队列里那些等待都写着在等谁。

### 二次处理（优化层：超分 / 插帧 / 重做）
```text
GET    /refine/kinds                              有哪几种处理（后端事实，前端不要硬编码）
POST   /projects/{pid}/refine/plan                只出账单：处理哪几段、用哪份图、哪几个跳过
POST   /projects/{pid}/refine/run                 按账单入队
GET    /projects/{pid}/versions/{vid}/lineage      血缘：{ancestors[], children[]}
```

目标三种给法（归一成 `[(version_id, shot)]`）：`version_ids`（版本轨里勾的，最精确）/
`shot_ids`（这些镜头**采用的那一版**，没采用过的跳过并说明）/ `scene_id`（整幕）。
输入**钉在某一版**而不是「这个镜头最新那版」：跑到一半换了采用，处理的还是当初那一段。

产物是**同一个镜头上的新版本**（`source="refined"` + `parent_version_id`），所以这里
**刻意没有采用端点**——采用全工程只有 `POST /versions/{vid}/current` 一个入口（硬约束 3），
旧版本一条都不删，不满意就采用回去。用哪份图：`refine.preset` → `video.preset`，
它必须标了 `AIVS_SOURCE_VIDEO`（见 docs/05 的 5.5），没标时 `plan` 回 `blocked=true` + `how_to`。

### 音源（配音 / 环境音：画面一个字节都不重跑）
```text
POST   /projects/{pid}/dub/plan                    只出账单：配哪几个镜头、说什么、多长
POST   /projects/{pid}/dub/run                     按账单入队（每条产出 kind="audio" 的一版）
POST   /projects/{pid}/shots/{shid}/audio/import    导入外面做好的音频（**不需要任何服务**）
GET    /projects/{pid}/shots/{shid}/audio-versions  这个镜头的音轨清单 + 当前采用哪一条
DELETE /projects/{pid}/shots/{shid}/audio-current   取消采用（回到画面自带的声音，版本不删）
```

- 台词只有一份口径（`dub.text_of`）：**显式 `text` → 镜头 `dialogue` → 幕 `dialogue`**；
  两者都空且没给声音描述（`prompt`）时这一条进 `skipped`，带四要素错误；
- `with_video=true` 把镜头采用的那段画面也送过去（口型驱动那类模型要它）；图里没有
  `AIVS_SOURCE_VIDEO` 时**只写一条 note，不失败**；还没出片时也不跳过，只标 `video_missing`；
- `voice_ref_asset_id` 是音色参考（几秒干净人声），非音频资产报 422；
- **没配音源不是异常**（硬约束 2）：`audio.provider="none"` 时 `plan` 照出（用户得先看见要配
  哪些），`run` 回 `MISSING_CAPABILITY`，建议里指向上面那条 `audio/import`——手动那条路走完全
  流程，装配、静音、配音轨全都照旧；
- 采用音轨**不在这里**：走 `POST /versions/{vid}/current`，它按 `kind` 落到
  `shot.current_audio_version_id`。

### 长视频导入切段（生成层的另一半：没有剧本、没有 LLM）
```text
GET    /ingest/methods                            有哪几种切点方法
POST   /projects/{pid}/ingest/register            登记源成片（copy_into_project，默认 true）
POST   /projects/{pid}/ingest/plan                只出账单：切几段、每段哪儿到哪儿
POST   /projects/{pid}/ingest/run                 才落库：一幕 + 每段一镜头一版
```

- `register` 默认**复制进工程**（`Asset.path` 相对工程目录存，整个目录拷走仍然有效）。
  `copy_into_project=false` 是原地引用，省磁盘，但返回值里的 `warnings` 必须显示出来：
  源文件一移动 / 改名 / 拔盘，从它切出来的所有镜头都会变成「文件不在磁盘上」；
- 切点三级降级（全靠内置 FFmpeg，账单里的 `method` 说清用的是哪一级）：
  `select='gt(scene,threshold)'` + `showinfo` → `silencedetect` → 固定窗口铺满。
  比 `min_segment` 短的相邻切点合并，合并掉哪几个写在 `merged_away` 里——**不是错误，但要说**；
- **切点是建议不是判决**：`plan` / `run` 都收 `cuts=[…]`，给了就不跑自动检测，
  账单上拖过的切点原样落下去（`method="manual"`）；
- **片头片尾在切段之前**：`plan` / `run` 都收 `range_in` / `range_out`（秒，留空 = 整段都要），
  切段只在这个区间里进行，**源文件一帧都不动**（区间只是一对数字，改主意重新出一次账单就行）。
  区间外的切点直接扔掉；账单回 `range_in` / `range_out` / `trimmed_head` / `trimmed_tail`，
  「少了一截」必须是界面上看得见的一句话，`run` 还把它写进幕的备注。
  保留区间不足 0.5 秒、或片头比整段视频还长时报 `VALIDATION_ERROR`（四要素齐全）。
  前端的第二步就是这一屏（`features/story/components/VideoTrimmer.vue`，
  拖两个手柄框出要保留的部分；原地引用的文件放不出画面，退化成填秒数）；
- `run` 落的是**一幕普通的幕**（`kind="ingested"` + `param_mode="shared"` +
  `source_asset_id`）+ 每段一个镜头 + 每段一版（`source="imported"`、`asset_id` 全指向同一个
  源文件、各自带 `in_point` / `out_point`）——**零文件复制**；
- 默认排在最后，`position` 给了就插到那一位并回 `scenes_shifted`（有几幕被推后）。
  顺序是用户的东西，动了必须说出来；之后照旧用 `POST /scenes/reorder` 随意穿插。

### AI 导演（协作栏，提案 + 逐条审阅）
```text
GET    /projects/{pid}/director                   {turns, llm: {configured, provider, model, hint}, note}
POST   /projects/{pid}/director/chat              {message, scope?} → {turns, ops, degraded}；**一行库都不改**
POST   /projects/{pid}/director/apply             {ops} → {applied, failed, count}
DELETE /projects/{pid}/director                   清空协作记录（已落库的改动不受影响）
```

`scope` 是「用户现在开着哪一页」（`script` 剧本页 / `flow` 幕流程图页，默认 `flow`）。它**只影响
这一次请求拼出来的系统提示词**里那一句，不落库、不分会话——两页共用同一份 `director_turn`，
换页不该让历史对话变味。

一条提案的形状（与 `story.propose_breakdown` 同一套规矩）：

```json
{ "op": "update_scene", "target": "scene", "temp_id": "op2", "scene_id": "scn_x",
  "before": { "title": "第一幕", "summary": null },
  "after":  { "title": "第一幕 · 雨夜" },
  "why": "标题要点出这一幕的天气，后面转场才对得上",
  "warnings": [] }
```

- `op` 就是写工具名。幕级：`add_scene` / `update_scene` / `set_scene_prompt` / `set_scene_cast` /
  `set_scene_props` / `set_link` / `reorder_scenes` / `delete_scene`（`target` = `scene` / `link`）；
  镜头级：`add_shot` / `update_shot` / `delete_shot` / `reorder_shots`（`target` = `shot`，
  带 `shot_id`）与 `set_shot_link`（`target` = `shot_link`）。用户**丢弃**一条时前端把
  它改成 `"reject"`，`apply` 只落 `op != "reject"` 的条目。
- **镜头 prompt 的三段字段只有一处口径**：`add_shot` / `update_shot`（以及 `add_scene` 的
  `shots[]`）收 `camera_motion` / `visual_prompt` / `audio_dialogue` / `negative_prompt` +
  `skill`（模型说它照哪一份 SKILL 写的），最终那段正向 prompt 由
  `prompts.format_shot_prompt()` 再过 `with_shot_audio_policy()` 拼成 `[SHOT n]` 四段格式写进
  `after.prompt`，界面上直接看得见。`update_shot` **没给的那几段从库里现有 prompt 解析出来补上**
  （`prompts.parse_shot_prompt()`），改一段不会把机位与对白擦掉。
- `set_shot_link` 的 mode **刻意只有 `cut` / `transition`**——镜头级的「续接末帧」已经有
  `shot.prev_shot_id` 这一种表达，不给它同义词。
- `before` / `after` 成对给，前端才能画出真正的 Diff：`before` 是库里现在的样子（新增时
  `null`；`add_shot` 例外，给 `{scene_title, shot_count}` 说清插进哪一幕、那幕现在几个镜头），
  `after` 是提案要改成什么（删除时 `null`）。
- `warnings` 是「能落，但有点不对」（角色名对不上任何角色）——对不上就写出来，绝不静默丢掉。
- `apply` **逐条独立落**：一条失败不回滚已经成功的那几条，`failed[]` 里每条带四要素错误。
  `reorder_shots` 落库前按**现在**这一幕有哪些镜头对一遍（同一批里可能有一条 `delete_shot`
  已经把某个镜头删了）：删掉的丢弃、没提到的排在后面。
- 读工具立刻执行，其中两个是「不再超时」的关键：
  - `read_script(offset, limit=2000)` 读剧本原文的一段，回
    `{total, offset, next_offset, done, text}`。模型自己分段读、一段一段地提案，每一轮 chat 的
    输入输出都是有界的；原文为空时报四要素错误（去剧本页贴一段再保存）。
  - `read_skill(name)` 取一份内置 SKILL 全文（`flf` / `i2v` / `l2v` / `ref`，见 docs/05）。
    **只有一行清单进系统提示词**，全文按需取；不认识的名字报 `VALIDATION_ERROR`。
- `llm.configured === false` **不是错误**：协作栏据此显示去设置页的引导，而不是一个红叉——
  流程图上手动加幕、改衔接、编排生成全都不依赖 LLM。
- `degraded: true` = 这个模型端不支持 function calling，走的是一次性产出 ops 数组的退化路径；
  提案形状完全一样（此时提示词里直接嵌一段原文开头，并说明取不到 SKILL 全文）。
- 工具循环上限 16 轮（分段拆解一轮里正常就是 `read_script` + `read_skill` + `add_scene` +
  若干 `add_shot`）。转满轮数时**先把提案落成 `director_turn` 记录再报错**
  （`LLM_INVALID_OUTPUT`，建议里写明「已产出的提案仍可审阅」）。

```text

GET             /projects/{pid}/assets/undescribed 还缺描述的那一批（不含 TRANSIENT_KINDS），带 owners / desc_max
POST            /projects/{pid}/describe/plan      只读账单：这几张能不能看图、会不会被跳过、上限多少
POST            /projects/{pid}/describe/suggest   出建议，**一行库都不改**；落库只有上面那个 PATCH
GET             /projects/{pid}/timeline
POST            /timeline/{tid}/commands          批量编辑命令（原子事务，返回新状态）
POST            /timeline/{tid}/auto-assemble

GET             /settings | PATCH /settings

POST            /settings/models                   {what: "llm", provider?, base_url?, api_key?}
GET|POST|DELETE  /settings/presets[/{name}]         ComfyUI 预设（模型端那份图的本地副本）
POST            /settings/presets/upload           multipart：file + name
GET             /system/gpu
```

`GET /settings` 每个字段回 `{value, source, ...}`（`source` = `file` / `env` / `default`，
生效顺序 **settings.json → 环境变量 → 默认**），密钥类字段**永不回明文**，只回
`{masked, has_value}`。`PATCH /settings` 按点号键提交（`"llm.base_url"`），值为 `null`
表示清除覆盖、回到环境变量；前端只在用户真的输入了密钥时才提交那个字段。

字段上另有两个**给 UI 用的开关，前端照它画界面而不是硬编码**：`choices` / `choice_labels`
一一对应（枚举项的人话标签），`fetch` 非空表示这一项的取值可以自动获取，值就是
`POST /settings/models` 的 `what`（当前只有 `llm.model` 是 `"llm"`）。顶层 `llm_protocols[]`
是**协议表的投影**（`{name, label, default_base_url, supports_tools, needs_key, models_hint}`），
`llm` 里除 `provider` / `configured` / `model` 外还带 `label` 与 `supports_tools`——
默认地址、要不要密钥、支不支持工具全部只有后端一份，加一个协议不用改前端。

`POST /settings/models` 是**「先试再存」**：带上还没保存的 `provider` / `base_url` / `api_key`
先列一遍模型（`api_key` 留空表示沿用已保存的那把），**绝不落盘**、绝不改动当前设置，
响应里也绝不回明文密钥。回 `{provider, label, target, count, items:[{id, label}], current,
current_present}`；`current_present === false` 是一条真警告——连得上但这个端上没有当前模型，
不然只有真正调用时才会失败。四种方言（OpenAI 兼容 / Anthropic / Gemini / Ollama）的差异全在
`app/ai/llm/protocols.py`，密钥一律走请求头，**任何协议都不把它放进 URL**。
未选协议（`provider="none"`）时是 `LLM_UNAVAILABLE`（503）且建议里写明手动路径；
`what` 不是 `"llm"` 时 `VALIDATION_ERROR`（422）。

`GET /settings/presets` 回 `{dir, items[], how_to[]}`，每条 `item` 是一份图的体检报告。
参考素材那几个键**按媒体分开给**，前端不自己数：

```json
{ "name": "wan-r2v", "ready": true, "r2v_ready": true, "flf_ready": false,
  "capabilities": ["r2v", "ref_video"], "first_frame_ok": true,
  "ref_slots": 9, "ref_video_slots": 2, "ref_audio_slots": 0,
  "ref_slots_by_media": { "image": 9, "video": 2, "audio": 0 },
  "ref_hint": "能收 9 张参考图（AIVS_REF_1、…、AIVS_REF_9）；另外还能收 2 个参考视频",
  "impact": null }
```

三条口径：**`ref_slots` 只数 `AIVS_REF_*`**（图片族），视频 / 音频各数自己那族——混成一个
总数会显示「能收 5 个参考素材」而其中 2 个只吃音频，用户照着塞图只会得到一个空跑的任务；
**0 槽不影响 `ready`**，但「参考图 0 槽」要标成警告（角色表喂不进去，形象只能靠首帧带），
而**参考视频 / 参考音频 0 槽是常态**，只在大于 0 时画徽标，否则会把前面那个真问题埋掉；
**上限是这份图的事实，不是设置项**——账单里的 `capacity` 就是从这里来的
（`context.project_ref_capacity` → `RefCapacity`），`video.ref_limit` 已经不再是上限来源。

Timeline 采用**命令数组**而非细粒度 REST，保证多步编辑的原子性与撤销对齐：

```json
{ "commands": [
  { "op": "split", "clip_id": "tcl_1", "at": 12.5 },
  { "op": "trim",  "clip_id": "tcl_2", "in_point": 1.0, "ripple": true },
  { "op": "replace_version", "clip_id": "tcl_3", "version_id": "gen_88" }
] }
```

### 跨环境搬迁：工程包 / 场景包（`.aivspkg`）
```text
POST /projects/{pid}/package/plan                    {include_generated}         → 导出账单
POST /projects/{pid}/package                         {out_dir, filename, include_generated}
POST /projects/{pid}/scenes/{sid}/package/plan       {include_generated}         → 单幕导出账单
POST /projects/{pid}/scenes/{sid}/package            {out_dir, filename, include_generated}
POST /packages/inspect                               {path}    → scope + counts + env 与本机的比对
POST /packages/import/project                        {path, dir}                 → 还原成一个新工程
POST /projects/{pid}/packages/import/scene/plan      {path}                      → 导入账单
POST /projects/{pid}/packages/import/scene           {path, reuse_by_name}
```

路由是 `/package` 而不是 `/export`：`POST /projects/{pid}/export` 早就是时间线那份 mp4 导出。
`/packages/inspect` 与项目导入不带 `pid`——导入的目标是一个**还不存在**的工程。
错误码全部复用已有的（`VALIDATION_ERROR` / `CONFLICT` / `NOT_FOUND` / `SCHEMA_MISMATCH` /
`DISK_FULL` / `MISSING_ASSET`），**没有新增 ErrorCode**。

**先账单再动手**（与采用同一套规矩）：`plan` 只读，返回体积账单 + `env` 要求清单 +
`omitted[]`「带不走的东西」+ `missing[]`「登记在册但文件已经不在磁盘上的资产」。
`omitted` 前端必须**原样显示**：跨幕的 `SceneLink`、指向幕外镜头的 `Shot.prev_shot_id`
（导入后置空）、`Job` 与队列历史、`Timeline` / `Track` / `Clip`、`DirectorTurn`。

**包的结构**（zip，`manifest.json` 的 `kind = "aivs-package"`，先认 kind 再解内容）：

```text
manifest.json      kind / package_id / package_version / scope / app / schema_version /
                   created_at / project{name,width,height,fps,duration_unit} / counts / env
project.db         仅 scope="project"：sqlite3 backup() 出来的快照（含 alembic_version）
data/scene.json    仅 scope="scene"：行级快照 + 文件清单
files/<相对路径>    assets/… 与（勾了才有的）generations/…，路径与工程内一致
```

`cache/` / `proxies/` / `.runtime/` **永不进包**（可再生），`settings.json` 也不进——
**密钥与服务地址一律不进包**，包里只有 `env` 那份**要求清单**：

```json
{"video_provider": "comfy_preset",
 "presets": [{"role": "r2v", "name": "wan_r2v", "markers": ["AIVS_PROMPT", "AIVS_REF_1"]}],
 "needs_ffmpeg": true, "needs_llm": false, "schema_version": 19}
```

**刻意不带预设图**：图属于用户那台 ComfyUI，本工具不维护它。`markers` 是导出机上那份预设
数出来的入口标题，目标机器没有同名预设时，清单至少能说出「要一份标了这几个入口的图」；
读不到那份图就只留 `name` + `unreadable: true`。`inspect` 把这份清单与本机逐条比对成
`env_check`（预设在不在、provider 配没配、schema 吃不吃得下），**只报告不抛**。

**四道门**（`import_project`）：目标目录已有 `project.aivs.json` → `CONFLICT`；已有无法识别的
`project.db` → 同 `POST /projects` 那条守卫；`manifest.schema_version` 比本机新 →
`SCHEMA_MISMATCH`（旧的不拦，解包后照旧 `upgrade_head` 并在响应里报 `migrated_from`）；
包内成员是绝对路径 / 带盘符 / 含 `..` 段 / 是符号链接 → `VALIDATION_ERROR`「包内路径越界」，
**这些检查全部在写第一个字节之前做完**。解包后**重新生成 project id**——`ProjectService._open`
是按 pid 索引的，同机导入一份副本后两个目录同 id 会互相顶掉。

**场景包的落库全部转调已有写路径**（`story` / `sequence` / `cast` / `world` / `assets`），
不新增写逻辑、不加迁移、不加列：素材按 sha1 去重（`assets.by_sha1` 命中就复用那条登记），
人物 / 地点 / 道具默认 `reuse_by_name=true` 按名字精确复用（同一部片子里多幕引用同一个角色是常态），
派生形象按父子拓扑序落；出处只记在 `Asset.meta.{package_id, package_sha1, imported_at}`。
`include_generated=true` 时只带**已采用的那一版**，导入走手动版本入口
（`source="manual"`，`params.imported_from_package`）——不伪造 job 血缘，硬约束 3 不受影响。
`ids.PREFIX` 只多了一项 `"package": "pkg"`。

打包 / 解包在 `asyncio.to_thread` 里跑，每 N 个文件往 `system` 频道发一条
`package.progress`（底部控制台已经在听这个频道）。写包是先落 `.tmp` 再 `replace`，
磁盘满（`OSError.errno == 28`）报 `DISK_FULL`。

### 文件服务与目录浏览
```text
GET  /projects/{pid}/files/{rel}   工程目录内的文件；支持 Range（时间线拖进度条要它）
GET  /library/files/{rel}          库目录内的文件
GET  /fs/roots                     盘符 / 家目录 / 桌面 / 文档

```

把 token 放在 query string 上的地方（`<img src>` 带不了请求头）。

## 5. WebSocket 事件

单端点 `/api/v1/ws?project_id=...&token=...`，客户端按 `channel` 订阅。

```json
{ "channel": "job", "event": "job.progress", "project_id": "prj_x",
  "ts": "2026-08-21T12:52:51.204431+00:00",
  "payload": { "job_id": "job_1", "shot_id": "sht_07", "progress": 0.62,
               "node": "KSampler", "step": 19, "total_steps": 30, "eta_ms": 41000 } }
```

**连线上只有一种信封**：`{channel, event, project_id, ts, payload}`，五个键一个都不许少。
握手帧 `system.connected` 与心跳 `system.ping` 也一样——它们曾经是 `api/ws.py` 里手写的字面量、
少了 `ts`，前端日志面板照契约读 `ev.ts.slice(...)` 就整块白屏。现在两条都过
`Event(...).to_dict()`，`tests/test_m0_foundation.py::test_ws_connect_and_receive_event`
拿 `set(hello) == {...}` 盯住这件事。

| event | 说明 |
|---|---|
| `job.queued` / `job.started` / `job.progress` / `job.completed` / `job.failed` / `job.cancelled` | Job 生命周期 |
| `queue.state` | 队列摘要（running/queued/waiting 数、是否暂停） |
| `shot.status_changed` | Shot 状态推导结果变更（含 `needs_review`） |
| `version.created` / `version.current_changed` | 版本变化，前端刷新 VersionRail 与 Timeline 徽标 |
| `asset.created` | 新资产（Sheet / 尾帧 / 代理） |
| `system.comfy_status` | ComfyUI 在线/离线、队列长度 |
| `system.gpu` | VRAM 占用、利用率（每 2s） |
| `error` | 结构化错误推送（进通知中心） |

约定：所有事件幂等、可丢失；前端在重连后必须调用对应 REST 做一次全量对齐（`/jobs`、`/shots`），不依赖事件流保证一致性。

## 6. 调度器行为规范

```text
tick():
  1. 认领：扫描 status=running 且本进程无内存句柄的 Job → 查 ComfyUI /history[prompt_id]
           命中 → 走 collector 完成；未命中且超时 → failed(COMFY_LOST)
  2. 就绪判定：status in (queued, waiting_upstream)
       strict 依赖 → 上游 job.status=completed 且 上游 shot.current_version_id 已确认
       optional 依赖 → 上游 job.status in (running, completed) 即可
  3. 排序：priority DESC, created_at ASC
  4. 派发：并发数 < worker_limit 时取队首 → resolve context → resolve workflow
           → adapter 构图 → POST /prompt → 记录 comfy_prompt_id → running
  5. 失败：分类错误码；可重试类（COMFY_OFFLINE / GPU_OOM）按 max_attempt 退避重排
```

- `worker_limit` 默认 1；用户可调，但 UI 需提示 VRAM 风险。
- 入队时用 Kahn 算法做环检测，失败返回 `DEPENDENCY_CYCLE` 及环路径。
- 队列暂停 = 不再派发新任务，正在跑的不中断。
- 任一 Job 完成后立即广播 `queue.state`，前端不轮询。

## 7. 生成产物落盘规范

```text
generations/<shot_id>/<version_id>/
├── request.json      GenerationRequest（含 ResolvedContext 快照）
├── graph.json        实际提交给 ComfyUI 的 prompt graph
├── result.json       ComfyUI 返回 + ffprobe 元数据 + 耗时
├── output.mp4        原始产物（不做二次编码）
├── first_frame.png   FFmpeg 抽首帧
├── last_frame.png    FFmpeg 抽尾帧（供下游继承）
├── thumb.jpg         320px 缩略图
└── proxy.mp4         720p / 密集关键帧 / 供预览与 Timeline
```

写入顺序：临时目录 → 校验完整（ffprobe 成功、时长 > 0）→ 原子改名 → 落库。任一步失败则清理临时目录并标 Job 失败，**不留半成品版本记录**。

**抽出来的首尾帧是临时资源，不进 `generations/` 也不进 `assets/`**：`services/frames.py` 是按需
（`tail_frame` 衔接、分镜板补首帧）抽的，落 `cache/frames/<sha1>.png`（`KIND_DIR["frame"]`）。
它仍然登记成一行 `Asset(kind="frame")` + `meta_json = {from_asset_id, at}`——上下文账单与
`generation._images_of` 都是靠 `asset_id → path` 取文件的。但它在 `assets.TRANSIENT_KINDS` 里，
所以**不出现在资产总账、也不算孤儿**（要看它们得显式 `?kind=frame`），并且**源成片一删就跟着删**
（`assets.delete` 回一个 `derived_removed[]` 说清删了哪几张，连带删除绝不静默）。
反过来单独删一张帧不动成片：它本来就是可再生的，需要时重抽一次。

素材库目录与工程目录同构，所以复用同一套落盘 / sha1 去重 / 尺寸嗅探逻辑：

```text
<用户自选的素材库目录>/
├── library.aivs.json   清单：kind: "aivs-library" + schema_version
├── library.db          SQLite（WAL）
└── assets/             取 KIND_DIR 里 assets/ 下的那几类，与工程侧同名（库不放生成物）
```

`library_asset.path` 相对**库目录**存，工程侧 `asset.path` 相对**工程目录**存——两边都能整体拷走。
